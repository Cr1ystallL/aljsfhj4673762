## 3. Глубокий анализ скриптов слива и удержания

В коде реализована сложная 5-уровневая система управления исходами. Ниже приведена полная картина того, как именно движок управляет балансом игроков.

### 3.1. Воронка депозита ("Качели") — `funnel-decision.ts`
Воронка активируется на первые **32 минуты** после пополнения счета (`FUNNEL_WINDOW_MS = 32 * 60 * 1000`):
1. **Фаза Hook (Крючок, bias = -0.30):**
   - Включается на 1-й депозит, пока баланс не превысил `депозит + 70 PLN` и вагер меньше `2.5 * депозит`.
   - Казино искусственно подкручивает генератор в пользу игрока. Игрок ловит дофаминовый всплеск, выигрывая первые ставки.
2. **Фаза Plateau (Плато, bias = +0.05):**
   - Баланс игрока находится в коридоре от `1.0x` до `1.85x` от депозита. Игра идет в около-нулевой динамике.
3. **Фаза Drain (Слив, bias = +0.40):**
   - Как только баланс игрока превышает `1.85 * депозит`, включается жесткий наклон в пользу казино, возвращающий игрока к депозиту.
4. **Фаза Recapture (Возврат выведенного, bias = +0.35):**
   - Включается на 2-й депозит игрока, если ранее он уже успешно выводил деньги из казино (`completedWdCount > 0`). Если его баланс поднимается выше `1.2x` от депозита, система включает слив, чтобы забрать выведенные ранее деньги.

---

### 3.2. Ловушка анти-скальпинга в Mines — `mines-click-decision.ts`
Именно этот скрипт порождает **ощущение жесткого скама**!
* **Суть проблемы:** В функции `decideMinesClick()` прописана защита от скальперов (тех, кто ставит на 3-5 мин и забирает 1.15x–2.20x после 1-го клика).
* **Формула вероятности подрыва (`scalpBustChance`):**
  ```typescript
  let p = 0.5;
  if (sessionProfit > 0) p += Math.min(0.24, sessionProfit / 90);
  if (betAmount >= 8 && sessionProfit >= 0) p += 0.08;
  if (betAmount >= 16 && sessionProfit > 5) p += 0.08;
  // Шанс подрыва на 1-м клике клампится до 86%!
  ```
* **Психологический шок для игрока:**
  Игрок выбирает поле 5×5 с **3 минами** (22 клетки безопасны, математический шанс выжить = **88%**).  
  Но если его ставка больше 16 PLN или он в небольшом плюсе (+10 PLN), алгоритм с вероятностью **86%** принудительно ставит мину под его ПЕРВЫЙ же клик!  
  Когда игрок на минимальном риске взрывается на первом нажатии 3 раза подряд — он закрывает приложение, пишет в чаты, что казино скриптованная помойка, и требует чарджбэк.
* **Результат в симуляции:** 5 288 случаев неестественных сливов на 400 человек и общий RTP Mines упал до **52.98%**!

---

### 3.3. SmartDrain и критический баг "Бесконечного слива" — `rtp-engine.ts`
* **Условия авто-включения SmartDrain:**
  - Серия побед $\ge 4$ подряд, ИЛИ
  - Профит за сессию $\ge +75\text{ PLN}$, ИЛИ
  - Единичный выигрыш $\ge +80\text{ PLN}$.
  - Игроку назначается `roundsLeft` = 4, 6 или 8 раундов со смещением `bias = 0.32`.
* **КРИТИЧЕСКИЙ БАГ РАСХОДА РАУНДОВ (`consumeDrainRound`):**
  В строках 856–857 `rtp-engine.ts` написано:
  ```typescript
  if (drainActive) {
    if (won) {
      await this.consumeDrainRound(userId);
    }
    return;
  }
  ```
  Раунд слива списывается **ТОЛЬКО КОГДА ИГРОК ВЫИГРЫВАЕТ**!  
  Если игрок проигрывает — счетчик раундов **НЕ УМЕНЬШАЕТСЯ**!  
  Игрок под действием слива проигрывает 5, 10, 15 раз подряд, а система считает, что у него по-прежнему осталось 6 раундов слива! Игрок гарантированно обнуляет весь свой баланс под ноль, если не прекратит играть на 20 минут.

---

### 3.4. Механизм Hidden Debt (Скрытый долг) — `rtp-engine.ts`
* Если игроку повезло поймать выигрыш $\ge 6\times$ от ставки (например, 10x на ставку 50 PLN = 500 PLN), чистая прибыль (450 PLN) записывается в `Hidden Debt`.
* Пока этот долг не равен нулю, в каждом раунде с вероятностью **50%** принудительно активируется `shouldForceLoss = true`.
* Долг списывается только по мере того, как игрок сливает свои ставки обратно в казино.

## 4. Критические уязвимости безопасности кассы

### 🔴 1. Бесконечный накрут баланса в CryptoBot Replay (`handlers/payment.py`)
* **Локация:** `handlers/payment.py` (функции `check_payment` и `auto_check_payment`).
* **Механика взлома:**
  При нажатии на кнопку "Проверить оплату" статус инвойса проверяется в Telegram CryptoPay API. Однако в базе данных нет проверки уникальности `invoice_id`. При удалении инвойса из словаря памяти срабатывает `fallback`:
  ```python
  if not invoice_data:
      db.add_balance(user_id, fallback_pln)
  ```
  Злоумышленник, оплатив 10 USDT, кликает по кнопке 50 раз через автокликер или параллельные запросы и получает на баланс 500 USDT, после чего ставит их на вывод.
* **Гонка с поллером:** Фоновый процесс `auto_check_payment` (каждые 10 сек) и ручной клик по кнопке параллельно начисляют баланс за один и тот же платеж.

---

### 🔴 2. Неавторизованный вебхук FoluxPay с фейковым балансом (`routes/foluxpay.ts`)
* **Локация:** `mini-app/apps/backend/src/routes/foluxpay.ts` (`POST /api/foluxpay/webhook`, строки 413–438).
* **Механика взлома:**
  Эндпоинт принимает входящие HTTP POST запросы **без проверки HMAC-подписи, без токена авторизации и без валидации IP-адреса шлюза**.
  В теле запроса код напрямую берёт поле `payload.paid_amount`:
  ```typescript
  const paidAmount = payload.paid_amount ?? order.amount_pln;
  await pool.query(sql`UPDATE balances SET amount = amount + ${paidAmount}::numeric WHERE user_id = ${order.user_id}`);
  ```
  Злоумышленник отправляет curl-запрос:
  `curl -X POST https://api.macvbet.com/api/foluxpay/webhook -d '{"order_id":"123","paid_amount":25000,"status":"completed"}'` — и получает 25 000 PLN на баланс.

### 🔴 3. Рассинхронизация SQLite в Telegram-боте и PostgreSQL в WebApp
* Telegram-бот хранит балансы в локальном файле `casino_bot.db` (SQLite).
* Mini-App хранит балансы в таблице `balances` в PostgreSQL.
* Игры внутри бота (Dice, Football, Mines) списывают и начисляют SQLite баланс, но НЕ обновляют `balances` в PostgreSQL.
* **Следствие:** Игрок, проиграв все деньги в боте, открывает Mini-App — и видит там старый баланс нетронутым.

### 🔴 4. MacvPot — 0% Rake + Эксплойт накрутки VIP-кэшбэка
* **Локация:** `games/macvpot/macvpot-engine.ts` (строка 325: `const netPot = round.totalPot;`).
* Комиссия казино равна **0%**. При этом пайплайн начисляет 1 VIP XP за каждые 10 PLN ставки.
* Два игрока (или один человек с 2 аккаунтов) переливают банк друг другу без комиссии, моментально прокачивают максимальный VIP-ранг и выводят ежедневный кэшбэк и бонусы за уровни (прямой вывод денег из казино с положительным матожиданием).

### 🔴 5. Отсутствие глобального Max Win Cap в `betting-pipeline.ts`
* В модуле ставок на спорт лимит зашит (`maxPayout: 50_000 PLN`).
* Однако в `bettingPipeline.processPayout()` для Crash, Mines, Wheel, Keno **нет общего потолка выплаты**!
* В Keno максимальный множитель равен **100 000x**. Если игрок поставит 50 PLN и угадает 7 чисел — движок зачислит ему **5 000 000 PLN**. Казино станет банкротом в одну секунду.

## 5. Математические ошибки в играх

### 5.1. Дисбаланс колеса фортуны (Wheel) — Сектор 30x имеет RTP 47.6%
* **Файл:** `games/wheel/wheel-engine.ts` (строки 587–592).
* Категории множителей:
  - 2x: вес 6.0 $\rightarrow$ шанс 47.62% $\rightarrow$ $RTP = 95.24\%$
  - 3x: вес 4.0 $\rightarrow$ шанс 31.75% $\rightarrow$ $RTP = 95.24\%$
  - 5x: вес 2.4 $\rightarrow$ шанс 19.05% $\rightarrow$ $RTP = 95.24\%$
  - **30x: вес 0.2** $\rightarrow$ шанс 1.587% $\rightarrow$ **$RTP = 1.587\% \times 30 = 47.62\%$**!
* **Ошибка разработчика:** Чтобы сектор 30x имел нормальный RTP 95.24%, его вес обязан быть **0.4** (тогда $0.4 / 12.6 \times 30 = 95.24\%$). Вес 0.2 срезал математический возврат сектора вдвое! Игроки, ставящие на 30x, проигрывают деньги в два раза быстрее нормы.

---

### 5.2. Crash Engine — Отключен Budget Cap
* **Файл:** `games/crash/crash-engine.ts` (строка 370: `const bias = 0; // Auto-RTP disabled for Crash`).
* Логика аварийного ограничения раунда по сумме выплат закомментирована.
* Если заходит хайроллер со ставкой 2 000 – 5 000 PLN на раунд, в котором честный генератор выбрасывает 150x, касса обязана выплатить до 750 000 PLN без какой-либо защиты.

---

### 5.3. Иллюзия Provably Fair в Coinflip
* **Файл:** `game-engine/provably-fair.ts` (строка 213: `coinflipOutcome(hash, choice, bias)`).
* Функция принимает `choice` (выбор игрока). Если генератор решил, что игрок выигрывает — монета падает стороной `choice`. Если проигрывает — противоположной.
* Криптографически это означает, что результат раунда **не зафиксирован заранее в хеше**, а подстраивается под нажатие кнопки игроком. Опытный игрок, проверив формулу верификатора, сразу поймет манипуляцию.

## 6. Архитектура и нагрузочная способность (500–1000 CCU)

**Конфигурация сервера:** 8 vCPU / 24 GB RAM / NVMe SSD (Ubuntu VPS `185.111.246.222`).

1. **Fastify Backend & WebSockets:**
   - Потребление памяти на 1000 активных вебсокетов: ~300 МБ RAM.
   - CPU при тиках Crash (100ms): ~12-18% от 8 ядер. Запас прочности огромный.
2. **База данных PostgreSQL:**
   - Все транзакции баланса защищены атомарными запросами `UPDATE balances SET amount = amount - X WHERE amount >= X RETURNING amount`.
   - Это исключает овердрафт баланса даже при параллельных запросах. Пул соединений рекомендуется выставить в `max: 35`.
3. **Узкое горлышко (Bottleneck):**
   - Python-бот на SQLite при 500 одновременных пользователях выдаст ошибку `sqlite3.OperationalError: database is locked`. Бот необходимо переключить на PostgreSQL.

## 7. Пошаговый план устранения проблем

### Фаза 1: Немедленные финансовые хотфиксы (Срок: 1 день)
1. **CryptoBot:** Добавить таблицу `crypto_invoices` в PostgreSQL с уникальным индексом по `invoice_id`. Исключить начисление баланса без атомарной транзакции смены статуса.
2. **FoluxPay:** 
   - Внедрить проверку подписи заголовка `X-Folux-Signature`.
   - Внутри вебхука вызывать `getOrderStatus(orderId)` и брать сумму исключительно из ответа самого шлюза.
3. **MacvPot:** Установить рейк казино в размере 4%:
   ```typescript
   const rake = round.totalPot * 0.04;
   const netPot = round.totalPot - rake;
   ```
4. **Max Win Cap:** Внедрить в `betting-pipeline.ts` жесткий глобальный лимит максимального выигрыша по любой одиночной ставке казино (например, `Math.min(credit, 50_000)`).

### Фаза 2: Калибровка скриптов слива (Срок: 1 день)
1. **Mines (`mines-click-decision.ts`):**
   - Убрать гарантированный `must_bust` на 1-м клике при низком множителе (< 1.50x).
   - Ограничить максимальный шанс подрыва на 1-м клике потолком **25%** вместо текущих **86%**.
2. **SmartDrain (`rtp-engine.ts`):**
   - Исправить баг сгорания раундов: раунд слива должен расходоваться на **каждой ставке**, независимо от победы или поражения (`roundsLeft -= 1`).
3. **Wheel (`wheel-engine.ts`):**
   - Изменить базовый вес сектора 30x с `0.2` на `0.4`, чтобы выровнять RTP до честных 95.24%.
4. **Crash (`crash-engine.ts`):**
   - Включить лимит максимальной суммарной выплаты на раунд (Round Budget Cap $\le 30\,000\text{ PLN}$).
